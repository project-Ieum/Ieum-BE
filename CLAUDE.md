# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

Greenfield Spring Boot skeleton generated by Spring Initializr — `IeumApplication` plus the Testcontainers test scaffolding are the only Java files; configuration has since been split into dev/prod profiles. There is no domain code, no controllers, no entities, and no Flyway migrations yet (`src/main/resources/db/migration/` is empty). Not yet a git repository.

Stack: Java 21 (toolchain-pinned), Spring Boot 4.1.1, Gradle 9.7.1 wrapper, PostgreSQL + Flyway, Spring Security, Lombok.

## Commands

The shell here is PowerShell, so invoke the wrapper as `.\gradlew.bat` (`./gradlew` under the Bash tool).

| Task | Command |
| --- | --- |
| Compile + test + jar | `.\gradlew.bat build` |
| Tests only | `.\gradlew.bat test` |
| Single test class | `.\gradlew.bat test --tests 'com.ieum.IeumApplicationTests'` |
| Single test method | `.\gradlew.bat test --tests 'com.ieum.IeumApplicationTests.contextLoads'` |
| Run the app (dev profile, local Postgres) | `.\gradlew.bat bootRun` |
| Executable jar | `.\gradlew.bat bootJar` |
| OCI image | `.\gradlew.bat bootBuildImage` |

Test reports land in `build/reports/tests/test/index.html`.

No linter or formatter is configured — `check` is just `test`.

## Configuration profiles — exactly two files, no shared `application.yaml`

There is deliberately **no `application.yaml`**. Config lives in two self-contained files, so reading one file tells you everything about that environment:

- **`src/main/resources/application-dev.yaml`** — local Postgres on `localhost:5432/ieum`, credentials from `DB_USERNAME` / `DB_PASSWORD`, SQL logging on, Flyway `clean` allowed.
- **`src/main/resources/application-prod.yaml`** — datasource from `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` (optional `DB_POOL_SIZE`, `SERVER_PORT`), logging quiet, Flyway `clean` disabled, graceful shutdown.

**No credentials exist anywhere in the repository** — both profiles read `DB_USERNAME` / `DB_PASSWORD` from the environment, deliberately with no fallback default. The two profiles intentionally share those variable names; a machine only ever runs one profile.

App name, JPA, and Flyway settings are duplicated in both files on purpose — that is the cost of the two-file rule. **Changing a shared setting means editing both files.**

Because there is no shared file, a launch with no active profile loads *no* config at all — not even `spring.application.name` — and dies with `Failed to configure a DataSource ... (no profiles are currently active)`. **`IeumApplication.main` therefore sets `spring.profiles.default=dev` via `SpringApplication.setDefaultProperties`.** That is the single source of the default, and it is deliberately in code rather than in Gradle so every launcher is covered: `bootRun`, `bootTestRun`, `java -jar`, and running the class straight from IntelliJ all fall back to dev with no run-configuration setup. `setDefaultProperties` has the lowest precedence, so `SPRING_PROFILES_ACTIVE=prod` still wins.

- Local: `.\gradlew.bat bootRun` logs `No active profile set, falling back to 1 default profile: "dev"`.
- Production: `SPRING_PROFILES_ACTIVE=prod java -jar build/libs/ieum-0.0.1-SNAPSHOT.jar`.
- **Tests bypass `main()`** — `@SpringBootTest` builds the context directly, so the default never applies to them. `build.gradle`'s `test` task sets `spring.profiles.active=dev` itself. Remove that and every test fails on a missing datasource.

Hibernate `ddl-auto` is `validate` in both profiles — Flyway owns the schema, so an entity without a matching migration fails startup on purpose.

## Database: local Postgres service only — Docker is not used

Both `bootRun` and `test` talk to the machine's native `postgresql-x64-18` Windows service on port 5432 (auto-start). **No Docker is required for normal development.** Two databases are needed:

| Database | Used by | Configured in |
| --- | --- | --- |
| `ieum` | `bootRun` (dev profile) | `application-dev.yaml` |
| `ieum_test` | `.\gradlew.bat test` | `build.gradle` — the `test` task overrides `spring.datasource.url` |

Neither database exists on a fresh machine; create them with the one-time setup below before anything will start.

The test database is **not visible in any yaml file**: the `test` task sets `spring.datasource.url` to `.../ieum_test` as a system property so tests reuse the dev profile's credentials and settings while keeping their Flyway migrations and data away from the development database. Change the test database there, not in yaml.

The login role is an **existing personal Postgres account reused from an earlier project**, not a project-specific one — which is exactly why its credentials live in environment variables rather than in the committed yaml. One-time setup on a fresh machine:

```
setx DB_USERNAME "<account>"
setx DB_PASSWORD "<password>"
psql -U <account> -d postgres -c "CREATE DATABASE ieum;" -c "CREATE DATABASE ieum_test;"
```

`setx` writes to the user environment, so both Gradle and IntelliJ see it — but **already-running IntelliJ windows and terminals keep their old environment and must be restarted.** A process started before `setx` will not see the variables.

### Failure mode when the variables are missing

Not what you would expect. Spring Boot's `@ConfigurationProperties` binding leaves an unresolvable placeholder as a literal string instead of throwing, so the driver receives `${DB_USERNAME}` as the username:

```
password authentication failed for user "${DB_USERNAME}"
```

Seeing a `${...}` placeholder inside a database error means the environment variable was never set — not that the password is wrong. (`@Value` would throw `Could not resolve placeholder` here; configuration-property binding does not.)

### Testcontainers is present but intentionally unused

`TestcontainersConfiguration` (a `PostgreSQLContainer` bean annotated `@ServiceConnection`) and `TestIeumApplication` are still in `src/test/java`, along with the three `testcontainers` dependencies — kept so the Docker path can be restored for CI or another machine. Nothing in the normal test run touches them. To re-enable Docker-backed Postgres:

- for tests: add `@Import(TestcontainersConfiguration.class)` back onto `IeumApplicationTests`;
- for running the app: use `.\gradlew.bat bootTestRun`, which resolves `TestIeumApplication` as the main class from the test source set.

Either way `@ServiceConnection` wins over `spring.datasource.*`, so the container's JDBC URL replaces the local one even with the dev profile active.

Do not bind a Docker Postgres to host port 5432 — both processes end up LISTENING, the native service wins the connection, and you get a confusing `password authentication failed for user "ieum"` instead of a port-in-use error. Use a different host port if you ever need a container alongside the service.

## Spring Boot 4 starter names

Boot 4 split the starters, so the familiar Boot 3 coordinates do not resolve. When adding dependencies to `build.gradle`, follow the existing pattern:

- `spring-boot-starter-webmvc`, not `spring-boot-starter-web`
- `spring-boot-starter-flyway` (plus `flyway-database-postgresql` for the Postgres dialect), rather than depending on `org.flywaydb:flyway-core` directly
- Test support is per-slice rather than one umbrella `spring-boot-starter-test`: `spring-boot-starter-webmvc-test`, `-data-jpa-test`, `-security-test`, `-validation-test`

## Conventions implied by the setup

- Base package `com.ieum`; the `@SpringBootApplication` class sits at its root, so component scanning only reaches subpackages of `com.ieum`.
- Schema changes belong in versioned Flyway scripts under `src/main/resources/db/migration` (`V1__*.sql`, …). Since Flyway owns the schema, keep JPA on validate/none rather than letting Hibernate generate DDL.
- Lombok is wired through `annotationProcessor` for both main and test source sets.
- Spring Security is on the classpath with no configuration, so every endpoint is currently locked behind the auto-generated basic-auth user until a `SecurityFilterChain` bean is added.
